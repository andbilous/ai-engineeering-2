    Порожня папка і Redis

    Збираємо API, яке робить коротке резюме звернення в підтримку і визначає його категорію. Модель справжня, через OpenRouter, тому кожен зайвий виклик коштує грошей і часу. Звідси й кеш, і ліміт, і фонова обробка.

    1. Створіть папку, поставте залежності, скопіюйте tickets.jsonl з репозиторію курсу (lesson-15-api-layer/data/) у data/.
    2. Запустіть Redis у Docker. Без Docker пропустіть цей рядок і поставте в .env USE_FAKEREDIS=1.
    3. Заповніть .env і додайте його в .gitignore до першого комміту.
    4. Запустіть агента в папці.
    Терміналmkdir ticket-api && cd ticket-api python3.12 -m venv .venv && source .venv/bin/activate pip install fastapi uvicorn httpx redis fakeredis pytest pytest-asyncio python-dotenv mkdir data && cp ../ai-engineeering-2/lesson-15-api-layer/data/tickets.jsonl data/ # шлях до вашої копії репозиторію курсу docker run -d --name redis -p 127.0.0.1:6379:6379 redis:8
    .envOPENROUTER_API_KEY=sk-or-... MODEL=openai/gpt-4o-mini API_KEYS=dev-key-1,dev-key-2,dev-key-3 REDIS_URL=redis://localhost:6379/0 USE_FAKEREDIS=0
    Терміналprintf ".env\n.venv/\n__pycache__/\n" > .gitignore git init && git add .gitignore data && git commit -m "start" claude

    Порт Redis прив'язано до 127.0.0.1: в офіційному образі protected mode вимкнено, і документація образу не радить відкривати порт назовні без пароля.

    Готово, коли docker exec redis redis-cli ping відповідає PONG (або стоїть USE_FAKEREDIS=1), git status не показує .env, агент запущений.
    Документація: Docker Hub → redis, fakeredis, OpenRouter → Quickstart

    Агент розпитує і пише SPEC.md

    1. Надішліть агенту запит нижче.
    2. Відповідайте на його питання за таблицею.
    3. Прочитайте SPEC.md і викресліть зайве: базу даних, реєстрацію користувачів, вебсторінку, WebSocket.
    4. Комміт.
    Запит агентуХочу зробити API для підтримки: на вхід текст звернення, на вихід коротке резюме і категорія. Деталей ще не продумав. Розпитуй мене, доки не зможеш написати специфікацію, а тоді запиши її в SPEC.md: правила з номерами R1, R2…, ендпоінти, коди помилок, формат подій стріму і що поза обсягом. Код не пиши. Що має бути: звичайна відповідь JSON, відповідь стрімом, кеш однакових запитів, ліміт запитів на ключ і пакетна обробка багатьох тікетів у фоні зі статусом. Обмеження: Python 3.12, FastAPI, Redis (у тестах fakeredis), httpx, pytest. Модель через OpenRouter, ключ і назва моделі в .env. Тікети для пакетної обробки в data/tickets.jsonl.
    Питання агентаВідповідь
    Що повертає POST /summarize?summary (до двох речень українською), category (одна з billing, bug, account, other), cached (true або false)
    Обмеження на текст?Порожній або довший за 4000 символів текст дає 422, модель не викликається
    Як перевіряти клієнта?Заголовок X-API-Key зі списку API_KEYS у .env. Немає або невідомий ключ дає 401, і це перевіряється раніше за ліміт і кеш
    Що вважати однаковим запитом?Той самий текст після обрізання пробілів по краях і заміни кількох пробілів одним, та сама MODEL і та сама PROMPT_VERSION. Ключ кешу: sha256 від цих трьох значень. TTL 1 година, temperature 0
    Який ліміт?10 запитів за хвилину на API-ключ, фіксоване вікно в Redis. 11-й запит дає 429 із заголовком Retry-After: скільки секунд до кінця вікна. Рахуються всі запити, навіть ті, що віддав кеш. /batch рахується як один запит
    Як працює стрім?POST /summarize/stream, Server-Sent Events. Події token з полем text, наприкінці done з повним summary, при збої error з message. Категорія в стрімі поза обсягом. Якщо клієнт відключився, запит до моделі закривається
    Як працює пакет?POST /batch з {"tickets": [{"id", "text"}]}, до 50 тікетів, відповідь 202 з job_id. GET /jobs/{id} повертає status (queued, running, done, failed), processed, total і results. Кожен тікет іде через кеш. Збій одного тікета дає в його результаті error, а job усе одно завершується. Чужий або невідомий job_id дає 404. Стан job у Redis з TTL 24 години
    Що, коли модель недоступна?502 з поясненням у detail. Помилку не кешувати
    Готово, коли у SPEC.md кожне правило має номер, записано порядок перевірок (ключ, потім ліміт, кеш, модель), формат подій стріму і розділ «поза обсягом».
    Документація: Claude Code → Brainstorm with Claude first

    Тести без мережі

    1. Почніть нову сесію.
    2. Надішліть запит на тести.
    3. Перевірте тести за списком нижче, допишіть або виправте хоча б один.
    4. Комміт.
    У сесії агента/clear spec-interview
    Запит агентуПрочитай @SPEC.md. Напиши pytest-тести в tests/ на кожне правило. Тести не ходять у мережу: клієнт моделі зроби залежністю FastAPI і підміняй через app.dependency_overrides на фейк, який повертає фіксовану відповідь і рахує свої виклики. Redis у тестах: fakeredis.FakeAsyncRedis. Код застосунку не пиши. Запусти pytest і покажи, що тести падають, бо застосунку ще немає.

    Перевірка тестів

    1. Другий однаковий запит повертає cached: true, а лічильник викликів фейку не зріс.
    2. Текст із зайвими пробілами потрапляє в той самий кеш, а інша PROMPT_VERSION ні.
    3. 11-й запит за хвилину дає 429 і Retry-After; запит без ключа лічильник не чіпає.
    4. Стрім: події йдуть у порядку token… done, а склеєні токени дорівнюють summary з done.
    5. Пакет з трьох тікетів, де фейк падає на одному: job стає done, у двох результатах є summary, в одному error.
    6. Помилка моделі дає 502, і наступний такий самий запит знову викликає модель.
    Готово, коли тести падають з помилкою імпорту чи 404, а не через помилки в самих тестах.
    Документація: FastAPI → Testing dependencies with overrides, fakeredis

    Запит агентуРеалізуй POST /summarize/stream за @SPEC.md через StreamingResponse з media_type="text/event-stream".     Кеш і 429 на живому сервері

    Тести вже перевірили логіку, тепер подивіться на неї на живому сервері: скільки часу займає запит до моделі і скільки відповідь із кешу, що лежить у Redis і коли сервер почне відмовляти.

    1. Надішліть двічі однаковий запит і порівняйте час. Свої цифри запишіть, на занятті 16 вони знадобляться.
    2. Подивіться ключі в Redis і їхній TTL.
    3. Надішліть 12 запитів поспіль і порахуйте коди відповідей.
    4. Подивіться заголовок Retry-After у відповіді 429.
    Час з кешем і безfor i in 1 2; do curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" -X POST localhost:8000/summarize \ -H "X-API-Key: dev-key-2" -H "Content-Type: application/json" \ -d '{"text": "Не можу увійти: пароль правильний, а система каже, що ні."}' done
    Що в Redisdocker exec redis redis-cli --scan docker exec redis redis-cli ttl "$(docker exec redis redis-cli --scan | head -1)"
    12 запитів поспільfor i in $(seq 1 12); do curl -s -o /dev/null -w "%{http_code}\n" -X POST localhost:8000/summarize \ -H "X-API-Key: dev-key-3" -H "Content-Type: application/json" -d '{"text": "Тест ліміту"}' done | sort | uniq -c
    Заголовок Retry-Aftercurl -si -X POST localhost:8000/summarize -H "X-API-Key: dev-key-3" \ -H "Content-Type: application/json" -d '{"text": "Тест ліміту"}' | grep -i -E "^HTTP|retry-after"
    Попросіть агента показати код ліміту. Якщо там INCR, а EXPIRE окремою командою лише тоді, коли значення стало 1, між ними можливий збій. Документація Redis називає це race condition: ключ лишиться без TTL, і клієнт застрягне в 429 назавжди. Виправлення: INCR і EXPIRE в одній транзакції (MULTI/EXEC) або Lua-скрипт.

    Ліміт рахує запити, а гроші залежать від токенів. Чи однакові для вас 10 запитів по 4000 символів і 10 запитів по 40? Відповідь знадобиться в ДЗ.

    Готово, коли другий запит має cached: true і помітно швидший, з 12 запитів 10 мають код 200 і 2 мають 429, а Retry-After не більший за 60.
    Документація: Redis → INCR, Pattern: Rate limiter, Redis → SET, RFC 6585 → 429 Too Many Requests
