# Чекліст рев'ю коду, написаного агентом

Проходьте його перед кожним комітом, який зробив агент. Відповідь «не знаю» означає, що цей шматок ви ще не прочитали.

## Що змінилось
- [ ] Я переглянув увесь diff, а не лише підсумок агента. Розмір diff відповідає задачі.
- [ ] Агент не чіпав `tests/`, `data/` і файли поза задачею.
- [ ] Нові залежності: кожна справді існує в PyPI, має живий репозиторій і потрібна. Назву перевірено вручну.

## Чи правильно
- [ ] Для кожного бізнес-правила R1–R9, якого торкається зміна, я знайшов рядок, де воно перевіряється.
- [ ] Я зламав одне правило навмисно (наприклад, `>` на `>=` у перевірці жорсткого ліміту R6) і бачив, як падає тест. Потім повернув.
- [ ] Граничні випадки: рівно бюджет, кешованих більше за вхідні, новий місяць, чужий проєкт.
- [ ] Помилки повертають код зі SPEC.md, а не `500`.

## Друга думка
- [ ] Рев'ю в новій сесії без історії, лише звіт, без змін.
- [ ] Для великої чи ризикової зміни: рев'ю моделлю іншого провайдера (наприклад, `codex exec`, `claude -p`, `gemini -p` з промптом «прочитай SPEC.md і git diff, знайди порушення, нічого не змінюй»).
- [ ] Кожна знахідка розкладена: виправити зараз / спитати чому / лишити. Розбіжності між рев'юерами перевірені руками.

## Безпека
- [ ] Користувач береться лише з `X-User`, а не з тіла запиту.
- [ ] SQL-запити параметризовані, без f-рядків з даними користувача.
- [ ] У коді, логах і комітах немає ключів і паролів.

## Чи зрозуміло
- [ ] Я можу пояснити кожну функцію своїми словами без допомоги агента.
- [ ] Немає мертвого коду, закоментованих спроб і дублювання логіки ліміту в кількох місцях.
